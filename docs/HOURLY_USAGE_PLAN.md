# 每日小时用量视图方案

状态：可行方案，尚未实现小时接口与页面。

## 数据边界

现有 `events` 保留逐次消费的 `at` 时间与 Token 分项；Codex、ZCode、Harness 的有效逐次证据可以按小时汇总。`UsageCube` 当前按上海日期派生日汇总，不能从日汇总还原小时分布。小时查询必须回到有真实时间的消费记录。

供应商须逐个判断：LMU 官方明细具有 `created_at`（服务端写入时间），可表达“记账时间”的小时趋势；只返回日统计、余额或额度的平台不能生成小时消费。日志时间也不等同于推理开始时间，不按调用耗时拆分 Token，不把一笔请求摊进多个小时。

## 界面

在现有趋势标题旁增加“按日／按小时”，保留曲线／柱状和指标切换。小时模式选择单个日期，提供前一天、后一天和日历；现有日期范围可用于圈定可选择日期。默认时区明确为 Asia/Shanghai，展示 00–23 时。提示显示小时区间、总量、输入、输出、缓存、请求数及时间含义；模型、来源、服务商、工作区和账户继续使用原筛选。

所选范围大于一天时先选某一天，不把多天的同一时刻偷偷相加。不支持小时粒度的来源显示原因，保留日视图；混合来源分别显示“逐次记录覆盖”与“仅日统计”，不把不支持部分补成零。当天未来小时为空，历史小时只有在来源覆盖已确认时才显示零，未扫描或查询失败用缺口状态。

## 查询

复用 `/api/usage/chart`，增加 `granularity=hour&date=YYYY-MM-DD&timezone=Asia/Shanghai`。服务器校验日期、时区和现有筛选，转换成 UTC 半开区间 `[start,end)`，查询带逐次时间且已核验、未退役的消费；不使用当前最近请求的 100 条上限。按小时以 BigInt 精确累加 Token，缓存与推理保留子集口径，费用使用现有精确金额计算。

结果包含 24 个时间桶、UTC 边界、来源覆盖、未知分项与数据版本；每桶的 `value=null`、已知零、部分覆盖明确区分。沿用来源请求身份去重与 fork 规则，不新建采集器、不重新联网补造历史。

先利用已有 `owner/at/source` 索引读取单日记录，测量查询计划与耗时；只有单日查询确实慢时才增加必要索引或增量小时派生表。缓存按 Profile、筛选、日期、时区、数据版本隔离，使用现有容量预算；新记录到达只失效相关日期，隐藏页面不轮询。取消请求及最新结果校验复用既有图表通道。

## 分步实施与核验

1. 核对各来源的逐次时间覆盖和时间语义，以真实证据确定可用列表。
2. 实现小时查询；先对照同日明细精确求和，逐项核验 Token、请求数与未知分项。
3. 接入既有趋势图组件和筛选状态，保持轴线、提示、浅深主题与切换连续性。
4. 用隔离资料覆盖 00:00、23:59、跨 UTC 日期、稀疏小时、同秒多次请求、重试、fork、超大整数、未知时间、日统计来源、慢请求和切换竞争。小时桶之和必须等于同样来源、日期和筛选的有效逐次明细；与日统计不同的覆盖另行说明。

建议先交付本机 Agent 的单日小时趋势，再按已验证的供应商逐步开放。该功能不承诺推理过程中每秒 Token 变化，也不能还原未曾采集的历史。

LMU 字段依据：[官方使用明细文档](https://docs.lmuai.ai/docs/api/usage-export)。项目计算口径见 [TOKEN_ACCOUNTING](../TOKEN_ACCOUNTING.md)。
